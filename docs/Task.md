**GameLauncher（WPF）P0~P4 规划**

### P0：核心闭环可用（Must-have，目标：可真实跑通一次完整更新 + 启动）
**目标**：本地/CI 可构建，对接真实或 mock CDN，成功完成「检查 → 增量下载 → 校验 → 启动游戏」完整闭环。

| 优先级 | 任务 | 说明 / 验收标准 |
|--------|------|-----------------|
| P0.1 | 补完现有 Checklist 剩余项 | 本地 `dotnet build` 验证（.NET 10 SDK）、真实 CDN 集成测试、真实 Unity Game.exe 联调。 |
| P0.2 | 配置与启动完善 | 支持 `launcher.json`（已有 example）、命令行参数、环境变量覆盖 `manifestBaseUrl` / `gameRoot` / `gameExe`。启动时自动检查更新或提供「强制检查」。 |
| P0.3 | 基础错误处理与日志 | 网络失败、哈希不匹配、路径逃逸、磁盘空间不足等有明确提示；写本地日志（或简单控制台）。 |
| P0.4 | ManifestTool 完善 | 支持排除规则（`.gitignore` 风格）、版本号注入、输出到指定目录；文档化「如何从 Unity 打包输出生成 manifest」。 |
| P0.5 | mock-cdn + 端到端测试脚本 | 提供可一键运行的 mock 流程（已有 mock-cdn 目录可扩展），验证「无变更 / 部分变更 / 删除文件 / 哈希错误」场景。 |

**完成标准**：在干净机器上，通过 CDN 下载增量后能正确启动真实游戏，且 Manifest 只在全部成功后更新。

---

### P1：可靠性与性能（Should-have，目标：生产可用级别）
**目标**：网络抖动、大文件、弱网场景下稳定可用，下载体验接近商业 Launcher。

| 优先级 | 任务 | 说明 |
|--------|------|------|
| P1.1 | 重试 + 指数退避 | 单个文件下载失败自动重试（可配置次数），支持取消。 |
| P1.2 | 断点续传（HTTP Range） | `.download` 文件支持 Range 续传，大文件中断后继续。 |
| P1.3 | 多线程 / 并发下载 | 可配置并发数（默认 4~8），带总进度与单文件进度。 |
| P1.4 | CDN 故障转移 | 支持多个 `manifestBaseUrl`（主备），主失败自动切备；或从 version-check 接口动态拿 CDN 列表。 |
| P1.5 | 带宽与限速控制 | 可选限速、优先下载关键文件（exe/dll 优先）。 |
| P1.6 | 进度与状态细化 | 当前文件、速度、剩余时间、总进度百分比、已下载/总大小。 |

**完成标准**：在模拟弱网/中断场景下，更新成功率 > 99%，大包（数 GB）体验可接受。

---

### P2：体验与集成（目标：用户可感知的完整 Launcher）
**目标**：UI 可用、与组织基础设施对接、基础运营能力。

| 优先级 | 任务 | 说明 |
|--------|------|------|
| P2.1 | WPF UI 升级 | 暗黑/现代主题、背景图/Logo、新闻公告区、版本号显示、设置页（路径、语言、自动更新开关）。参考 Battle.net / Steam 简洁风格。 |
| P2.2 | 与 game-core / MP 对接 | 启动时可选调用 version-check 接口（获取最新版本 + Manifest URL）；支持 JWT（从 MP 登录后带 token）。 |
| P2.3 | 安装与首次引导 | 首次运行选择安装目录、磁盘空间检测、创建桌面/开始菜单快捷方式。 |
| P2.4 | 自更新（Launcher 自身） | Launcher 自己也走同样的 Manifest 机制更新（独立小包）。 |
| P2.5 | 多语言与本地化 | 至少中英，预留扩展。 |
| P2.6 | 设置持久化 | 用户偏好、上次路径、跳过更新选项等。 |

**完成标准**：用户从下载 Launcher → 安装游戏 → 日常更新 → 启动，全程体验流畅，无明显技术感报错。

---

### P3：高级能力与运维（目标：可规模化运营）
**目标**：支持更复杂发布策略、诊断、多游戏/多渠道。

| 优先级 | 任务 | 说明 |
|--------|------|------|
| P3.1 | 差量补丁增强 | 支持二进制 diff（如 bsdiff / hpatch）可选，进一步减小增量体积（大文件场景）。 |
| P3.2 | 预下载 / 后台更新 | 游戏运行中可后台检查并下载（不强制立即替换）。 |
| P3.3 | 完整性校验模式 | 一键「验证游戏文件」全量 re-hash。 |
| P3.4 | 诊断与上报 | 集成 BugReport 组件；失败时收集环境信息（系统、磁盘、网络）一键上报。 |
| P3.5 | 多游戏支持 | 一个 Launcher 管理多个游戏（Catalog 来自 MP），切换游戏根目录与 Manifest。 |
| P3.6 | 渠道与发布管线 | 支持 Steam / 官服双渠道配置；CI 自动生成 Manifest + 上传 CDN；版本灰度（按账号/设备）。 |
| P3.7 | 安全加固 | Manifest 签名验证、HTTPS 强制、路径白名单更严格、防篡改。 |

**完成标准**：可支撑正式公测/上线，运营可灰度、可快速回滚、可诊断用户问题。

---

### P4：长期演进（Nice-to-have / 未来方向）
**目标**：平台化、体验极致、技术债清理。

- 跨平台（Avalonia 或 .NET MAUI 考虑 Linux/macOS）。
- 插件化（自定义启动参数、MOD 管理、社区内容）。
- 智能调度（根据用户网络/地区选最优 CDN、P2P 辅助下载）。
- 深度分析（更新成功率、平均下载时间、失败原因分布仪表盘，对接 GameDashboard）。
- 安装包体积优化、静默更新、多账号切换等高级功能。
- 与 HybridCLR 路线明确边界（本 Launcher 专注 PC 文件级更新，手游走另一套）。

---

### 推荐落地顺序与里程碑建议
1. **立即做完 P0**（1~2 周）：把 Checklist 剩余项 + 真实联调搞定，确保「能用」。
2. **P1 并行推进**（2~3 周）：可靠性是上线前必须。
3. **P2 与 P1 后期重叠**：UI 和集成可以边做边用。
4. **P3 在正式公测前启动**。
5. **P4 视业务优先级再排**。
